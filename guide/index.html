Two client paths, clear boundaries

Native SMF automation and a Go rules shim.

The Python client provides durable buffering and managed queue migration. The Go shim adds topic and payload rules, AMQP, asynchronous publication and application-controlled acknowledgement. Its memory-only queue does not yet provide the same restart guarantees.

One API for your application

Publish a topic. Subscribe to what matters.

The shim finds the broker and keeps connections and consumers in step with the controller. Solace matches native topic subscriptions and delivers each group's copy.

Application code
client.subscribe(
    group="ledger",
    handler=commit_payment,
)
client.publish(
    "payments/account-42/created",
    {"amount": 25},
    event_id="payment-123",
)

Publish saves locally and returns. Broker receipts arrive asynchronously; no subscriber reply is required. Handlers deduplicate event IDs.

YAML controls what spreads

Spread by business key, spread by full topic, or keep a topic family together. Declare subscriber groups and set scaling thresholds and cooldowns per shard.

Solace does the fanout

Ledger subscribes to all payments; audit subscribes only to created payments. Each group has durable queues. Replicas share a group's exclusive queues.

The shim follows the move

Bind new receivers, buffer rejected writes, drain old queues and resume on the new owner. Applications keep using the same API.

How messages are spread

A business key is better than a turn in a queue.

The original resolver balanced client placement counts. That cannot distinguish a quiet client from a very busy one. The new partition option keeps messages for the same order, account or device together.

Same key, same partition

Use the smallest business key whose events must stay together. A huge tenant can still become one hot key if you route only by tenant ID.

New broker, limited change

Rendezvous hashing changes only winners that prefer the new broker. Optional weights reflect relative tested capacity, not queue depth.

Durable queues keep their owner

Recorded guaranteed partitions do not move on lease expiry. If every partition is assigned, adding a broker moves zero existing traffic until a controlled migration.

Choices you can configure today

Business rules in a small YAML file.

For native messaging, YAML extracts the business key from the topic. The controller creates group queues and native subscriptions; the shim manages publishing and receiving.

payments.yaml 
version: 1
connection: connection.yaml
scaling:
  mode: automatic
  max_brokers: 4
  warm_brokers: 1
workloads:
  payments:
    topic: payments/{account}/{event}
    keep_together: account
    subscribers:
      ledger: payments/>
      audit: payments/*/created

Keep broker connections and measured capacity in an operator profile. Run explain to inspect these rules, then start serve and run with the same policy.

Choose how to group traffic

keep_together: account uses a named topic field. Choose topic for each complete topic or all to keep the entire workload together.

Set the capacity ceiling

max_brokers caps active and warm services per workload. warm_brokers reserves ready capacity within that ceiling.

Pause new moves

mode: paused stops new moves while existing handovers finish safely. Automatic mode responds to sustained measured load.

Keep the partition contract stable

Changing partitions requires migration. A lease controls the location cache, never the lifetime of a durable queue owner.

Initial ownership uses the selected routing strategy. Enable the automatic controller to move existing managed queues by measured load. A lease never substitutes for broker-enforced fencing and confirmed drainage.

While you are away

A payment burst needs more than a new broker.

The controller selects an existing partition that fits on spare capacity, then moves its ownership through a recorded handover. Other partitions continue processing.

Grace plus drainage

Elapsed time never permits abandoning a payment. Queued, stored and unacknowledged messages must all reach zero, and the new consumer must be bound.

Buffer and retry

The old broker rejects stale publishers. A persistent outbox retains rejected or uncertain messages. Business handlers deduplicate event IDs in their own transaction.

Keep spare capacity ready

Use warm brokers immediately. Optional Cloud provisioning replaces spares within the broker ceiling. Cold provisioning takes time; the buffer applies backpressure when full.

Recover after restart

Resume the recorded phase from persistent local state. Before ownership changes, a timeout can recover toward the original queue. After the switch, recovery finishes forward.

Start with a question, not a deployment

How many brokers would this workload need?

Import your measurements, compile one matching generation, and size a hypothetical workload. Every command below is read-only with respect to your brokers.

terminal · Python 3.11+
pip install -e './scaling-controller[compile,service]'
solace-autoscale profiles import --directory /path/to/workbooks
solace-autoscale profiles list

# Choose a catalog and supply actual HA VPN limits.
solace-autoscale profiles compile \
  --catalog resources/performance/catalog/PROFILE.json \
  --service-classes your-ha-limits.json \
  --limits-source "Deployed VPN limits, checked today" \
  --out models/my-profile.json

solace-autoscale plan --model models/my-profile.json \
  --service-class enterprise-1k --message-size 1024 \
  --messages 10000 --fanout 5 --scenario streaming

The workload inputs above are illustrative. Physical spool disk size is not the configured VPN spool limit.

IMPLEMENTED

Planning, observation and assignment

Measured imports with provenance. Direction-aware capacity calculations. Complete fleet snapshots. Fixed key partitions. Weighted rendezvous. Durable single-host SQLite transactions. Python lease caching. One publish/subscribe API with native topic fanout and durable publisher retry. Automatic load-aware handover, restart recovery and optional warm-pool replenishment.

VALIDATE BEFORE ROLLOUT

Production validation and wider scope

Managed SMF handover passed a real two-broker test; Cloud creation is mock-tested. Production Cloud permissions, networking and workload performance still need validation. Multi-host controller HA, automatic scale-in, backlog copying and arbitrary existing queues are outside this implementation.

A hot key, a slow consumer, and an undersized broker are different problems. More brokers cannot fix all three. Validate your real workload, queue ownership and recovery requirements before production use.
